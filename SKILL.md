# 1. What this project is
A command-line tool that answers questions about Qdrant's documentation by retrieving the most relevant doc excerpts and feeding them to an LLM. To an engineer: a hybrid (vector + keyword) retrieval-augmented generation pipeline over a markdown corpus, with a measured retrieval evaluation harness instead of just a demo.

# 2. Problem it solves
Searching long technical docs by keyword misses conceptually related answers; reading the whole doc set to answer one question is slow. This lets you ask a natural-language question and get an answer grounded in the actual docs, with the source file shown so you can verify it. Built specifically to learn how retrieval quality is actually measured, not just to wrap a library.

# 3. Architecture
```
docs/*.md → chunk → embed (local) → Qdrant (vector store)

question → embed → hybrid search (Qdrant) → top-5 chunks → Groq LLM → answer + sources
```

Components:
- `ingest.ts` -> chunks and embeds markdown docs, loads into Qdrant -> batch upserts avoid request timeouts on large doc sets
- `embed.ts` -> generates embeddings via `@xenova/transformers` (local) -> avoids API cost/rate limits vs. OpenAI embeddings
- `qdrant.ts` -> Qdrant client/collection config -> chosen over pgvector for native hybrid-search support and a free managed cloud tier
- `search.ts` -> hybrid retrieval (vector similarity + keyword-overlap boost) -> pure vector search misses exact-match terms (API names, config keys)
- `cli.ts` -> interactive query loop -> replaced a hosted Express API to cut scope; no server/deployment to maintain
- `eval.ts` -> retrieval evaluation harness (precision@5) -> the one piece that proves retrieval quality rather than assuming it

# 4. Key decisions and trade-offs
| Decision | Options I considered | What I chose | Why | What I gave up |
|---|---|---|---|---|
| Embeddings | OpenAI `text-embedding-3-small` vs. local `@xenova/transformers` | Local (`all-MiniLM-L6-v2`) | Zero API cost, no rate limits | Lower embedding quality than OpenAI's model |
| Chunking | Semantic/AST-aware vs. fixed-size | Fixed-size (500 words, 50 overlap) | Simple, fast to implement for project scope | Chunks can split a concept mid-explanation |
| Search | Pure vector vs. true BM25+vector vs. hand-rolled hybrid | Vector + keyword-overlap boost (weighted merge) | Qdrant-native vector search plus a cheap keyword signal | Not a real BM25 sparse index |
| Interface | Hosted Express API vs. CLI | CLI | No deployment/hosting to maintain, faster to finish | No live clickable demo link |
| LLM | OpenAI/Claude vs. Groq | Groq (Llama 3.3 70B) | Free tier, fast inference, no card | Slightly less capable model than GPT-4/Claude |
| Runtime | Python (RAG-ecosystem default) vs. Node.js/TypeScript | Node.js/TypeScript | Matches existing backend stack, no context-switch | Smaller RAG-specific library ecosystem |

# 7. Things that broke and how I fixed them
1. Symptom: `ts-node` crashed with `TypeError: Cannot read properties of undefined (reading 'fileExists')` on startup
   Cause: version incompatibility between `ts-node` and the installed Node/TypeScript versions
   Fix: switched to `tsx` as the TS runner
   Lesson: default to `tsx` over `ts-node` for new projects — fewer config conflicts
2. Symptom: TypeScript error — `A top-level 'export' modifier cannot be used... when 'verbatimModuleSyntax' is enabled`
   Cause: `tsc --init` enabled a stricter ESM-oriented flag not needed for this CommonJS project
   Fix: set `verbatimModuleSyntax: false` in `tsconfig.json`
   Lesson: check `tsconfig.json` defaults generated by newer TypeScript versions before assuming code is wrong
3. Symptom: `Could not find a declaration file for module 'express'`
   Cause: `@types/express` wasn't actually installed (or was removed) despite being in the original setup
   Fix: reinstalled `@types/express`
   Lesson: Express requires separate `@types` packages since it has no built-in TypeScript types

# 8. What I would do differently at 100x scale
- Replace fixed-size chunking with structure-aware chunking (split on markdown headers/code blocks) to reduce mid-concept splits
- Replace the hand-rolled keyword boost with a real sparse-vector/BM25 index (Qdrant supports this natively)
- Add a retrieval confidence threshold with an explicit "insufficient context" fallback instead of always forwarding top-5 chunks to the LLM

# 9. Interview answers I have rehearsed
Q: How did you evaluate whether your RAG system actually works?
A: I wrote 30 question/expected-source pairs by hand against the ingested docs, ran each through my search pipeline, and measured precision@5 — whether the correct source file showed up in the top 5 results. That gave me a concrete number instead of just eyeballing whether answers looked plausible, which matters because an LLM can sound confident even when retrieval pulled the wrong context.

Q: Why hybrid search instead of pure vector similarity?
A: Pure semantic search misses exact-match terms like function names or config keys, since embeddings capture meaning, not literal strings. I added a keyword-overlap boost on top of vector similarity so exact terms in the query get weighted up, which is a simplified version of what BM25+vector hybrid search does in production systems.

# 10. Honest limitations
This does not use a real BM25 sparse index — the "hybrid" search is a hand-rolled keyword-overlap boost, not production-grade hybrid search. Chunking is fixed-size, not structure-aware, so answers spanning a chunk boundary can retrieve incomplete context. There's no confidence threshold — the system always passes its top-5 results to the LLM, even when none are good matches. The eval set is 30 questions, which is enough to catch gross failures but not statistically robust. There is no hosted/live version — it runs as a local CLI tool.

# 11. How to run it
```bash
git clone <repo> && cd rag-docs-qa
npm install
cp .env.example .env
npx tsx src/ingest.ts
npm run ask
```

Required environment variables: `QDRANT_URL`, `QDRANT_API_KEY` (blank for local Qdrant), `GROQ_API_KEY`
